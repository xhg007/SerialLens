# M0 / M1 验收记录

- 日期：2026-11-13
- 分支：`feat/m0-m1-foundation`
- 环境：Windows 10 Pro 22H2 (19045) / AMD64；Go（`go.mod` 1.26.0）；Wails v3.0.0
- 串口链路：com0com 3.0.0.0 signed（`CNCA0 PortName=COM11` ↔ `CNCB0 PortName=COM12`），驱动经 `pnputil /add-driver com0com.inf /install` 入库
- 工具：`cmd/loopcheck`（走生产链路 `SerialService` → 读循环 → 33ms 合帧 → `serial:data`，非同构重写的裸读）
- 前置说明：本机无 gcc，`go test -race` 不可用（`CGO_ENABLED=0`），并发正确性由定向单测覆盖（重连、尾部 flush、goroutine 计数），race detector 留待 M2。

## 一、115200 限速 60 秒（主判据）

```
go run ./cmd/loopcheck -tx COM11 -rx COM12 -baud 115200 -rate 11520 -bytes 691200
```

```
flush-on-stop: before=691200 after=691200 (+0)
sent=691200 received=691200 events=1350
frames: ok=10800 expected=10800 missing=0 dup=0 corrupt=0
elapsed=1m0s throughput=11520 B/s (92160 bps) maxEventGap=69ms
PASS: 0 丢包 / 0 重复 / 0 内容错配
```

- 10800 帧 = 691200 / 64，帧序号 0..10799 连续无缺口
- 吞吐 11520 B/s 与 8N1@115200 的理论上限（115200/10）完全一致
- `maxEventGap=69ms` 为偶发调度抖动，仍低于 UI 判据 100ms

## 二、921600 高速档 30 秒（余量验证）

## 三、降级链路（`-loopback`，未覆盖驱动）

```
go run ./cmd/loopcheck -loopback -rate 0 -bytes 65536
sent=65536 received=65536 events=1
frames: ok=1024 expected=1024 missing=0 dup=0 corrupt=0
PASS
```

用途：在无驱动环境（CI/新机器）验证「读循环 + 合帧 + hex 事件」管线的完整性；**不证明** go.bug.st 驱动路径。

## 四、突发模式（`-rate 0`）的装置限制

| 发送 | 收到 | 说明 |
| --- | --- | --- |
| 1 024 B | 512 B | 只保留首个 512B 块 |
| 65 536 B | 512 B | 同上；写入端全量返回成功但驱动静默丢弃 |
| 64 KB（`-chunk 256`） | 512 B | 与分块大小无关 |

结论：com0com 的写入端不阻塞、接收缓冲满即丢弃，**不具备突发缓冲语义**；真实串口按波特率逐字节流动，物理上也不存在「瞬时 1MB 突发」。因此 `-rate 0` 不作为验收判据，仅保留为诊断模式。突发缓冲能力应在 M2 用真实硬件（USB-Serial 回环）复测。

## 五、UI 冻结度量

方法与指标：

- `frontend/src/devProbe.ts`（仅 DEV 动态加载，生产构建已被 tree-shake，包体对比无变化）用 `requestAnimationFrame` 采样相邻帧间隔，暴露 `window.__slDevStats()` 的 `frames / maxGapMs / p99GapMs / lines`
- 通过 Wails MCP（`WAILS_MCP=1`）驱动真实窗口：选中 COM12 → 点击「打开串口」→ `loopcheck -sendonly` 从 COM11 灌流
- 窗口置顶聚焦，采样期间不做其他操作，避免 WebView2 对遮挡窗口的 rAF 节流污染样本

结果（92160 B/s 灌流、终端约 5000 行、30 事件/秒）：

| 指标 | 数值 |
| --- | --- |
| 平均帧率 | 约 56 fps（1126 帧 / 20 秒） |
| 最大帧间隔 | ≤ 100 ms（个别帧） |
| 99 分位帧间隔 | 83 ms |
| 终端行数 | 持续增长至 5000 行上限后稳定 |
| RX 计数 | 实时刷新（1 Hz），累计值与发送字节一致 |

结论：**未出现冻结**（无秒级卡顿，灌流期间开关/暂停/清空按钮可响应，终端持续追加）。5000 行满额时仍有 83–100ms 的偶发长帧，根因是满额列表的全量 React 协调与滚动定位；已用「100ms 批量提交 + `content-visibility:auto` 跳过屏外行」缓解，彻底方案（虚拟滚动）留待 M3 图表/终端联调时实施。

### 采样期间修复的两个 UI 缺陷

1. **尾部数据滞留**：`readLoop` 把阻塞 `Read` 与合帧定时器放在同一 select 循环里，设备发完最后一帧就安静时，`pending` 会滞留到下一次数据（实测 15s+）。改为「独立读 goroutine + select 驱动 flush」，并新增回归测试 `TestSerialServiceFlushesTailWhenIdle`。
2. **RX/TX 计数不刷新**：`serial:status` 只在连接/断开时发射，流式期间计数冻结在 0。改为 1 Hz 节流推送，新增回归测试 `TestSerialServiceEmitsStatusWhileStreaming`。
